# Production 解析扩展维护说明

自定义功能在 `production` 维护，`main` 用于追踪上游。当前先保持以下策略，边使用边观察，
不增加新的解析后端、代理或跨机器人调用。

| 平台 | 当前策略 | 实现与详细说明 |
| --- | --- | --- |
| Instagram | 配置了 Cookie 时优先使用；未配置时保持匿名流程 | `extensions/instagram_cookie.py`；[详细说明](instagram-cookie.md) |
| TikTok | 视频优先网页，失败回退 App；图文仍使用原 App 路径 | `extensions/tiktok_web.py`；[详细说明](tiktok-web.md) |
| YouTube | 保持上游现有实现与配置，本轮没有修改 | 无额外扩展 |

## 接入点与更新检查

两个扩展在 `services/parser.py` 创建 `ParseHub()` 后启用；服务另有 TikTok 专用外层重试预算和限流停止判断。
不修改 ParseHub 安装目录或全局解析器注册表，不改 Cookie 文件和依赖版本。

同步上游后：

1. 确认服务中的两个接入调用仍保留。
2. 在项目依赖环境中运行 `python -m pytest`；测试使用虚构 Cookie 和模拟响应，不访问平台。
3. 重点检查首个 Instagram 请求携带 Cookie、TikTok 网页优先及 App 回退、图文和短链兼容。
4. 如果上游已修复相同问题，评估移除对应扩展，避免长期叠加重复逻辑。

## 观察口径

- 请求统计的成功表示机器人完成该次处理，包含缓存命中，不等同于实时解析成功率。
- 可用 `/jxjx <链接>` 绕过缓存做少量人工测试；不建议对失败链接连续高频重发。
- 当前 INFO 日志可核对请求、最终失败和 Bot 外层重试；TikTok 双路径失败包含 `web` / `app` 各自原因。
  这些日志仍不能用于精确统计所有内部 HTTP 请求，包括短链重定向。
- 分别观察成功率、完整交付耗时及错误类别；不要仅凭 HTTP 200 或一次成功判断 Cookie 永久有效。
