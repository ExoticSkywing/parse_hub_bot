# 鹿源源管理员统计

在 `production` 分支维护。机器人仅在管理员私聊中响应，不把管理员命令加入公共菜单。

## 配置与使用

在本地 `.env` 中设置，再重新创建容器使环境变量生效：

```dotenv
USAGE_ADMIN_IDS=1861667385
USAGE_TIMEZONE=UTC
```

多个管理员用英文逗号分隔。必须填写数字 Telegram 用户 ID，不能使用用户名。
未配置或配置无效时，不向任何账号提供统计查询。时间默认为 UTC；例如可改为
`Asia/Shanghai` 或 `America/Los_Angeles`，统计回复会注明时区。

向机器人私聊发送：

- `/stats`：统计启用时间、累计接触用户、今日和近 7 天活跃、累计及今日请求、成功率。
- `/user`：浏览最近用户，每页 10 人，显示数字 ID、最近使用时间、累计解析次数。
- `/user 1861667385`：某个账号首次接触、最近使用、累计请求和近期请求时间、结果。

启动时自动为已配置管理员设置专属私聊菜单，保留原有命令并追加 `/stats`、`/user`；
公共菜单不变。专属菜单使用机器人默认语言，新增统计命令使用中文说明。
点击 `/stats` 可直接查询；点击 `/user` 打开列表，再点击用户按钮查看详情，无需事先知道 ID。
列表正文和详情标题中的数字 ID 均为 `tg://user?id=<ID>` 主页链接，点击打开该用户个人主页，
不再是点击复制的代码文本。两个页面均不提供独立的“打开主页”按钮：列表下方保留查看统计及翻页按钮，
详情页底部只保留“返回用户列表”。按 ID 直接查询和从列表点选进入详情的布局一致。
无需用户名，不新增统计数据库字段。
能否打开受对方隐私设置、与机器人的交互情况及客户端支持限制，不能保证所有账号都可访问；
主页无法打开不影响统计查询。旧列表可点击“刷新”或重新发送 `/user` 显示新布局；
旧详情需点击“返回用户列表”后重新查看用户，已发送的历史消息不会自动改写。
支持上一页、下一页、刷新，以及从详情返回原页；在同一条消息中更新，不反复发送列表。
列表只包含统计启用后接触过机器人的用户（含解析次数为 0 的用户），按最近使用时间倒序排列，
时间相同按数字 ID 倒序排列；刷新或翻页时读取最新数据，新活动可能使用户所在页变化。
不额外查询 Telegram 昵称或用户名。每次翻页、刷新和查询详情都会重新验证管理员身份和私聊范围；
正文中的 ID 链接不触发机器人回调，不读取统计数据。
Telegram 客户端可能需要关闭并重新打开聊天才显示更新后的菜单。
管理员需先与机器人建立私聊；若日志提示菜单设置失败，可在建立私聊后重启机器人重试，
期间仍可手动发送命令。菜单只提供入口，查询权限仍由每次请求的管理员校验控制。

用户详情最多显示最近 10 条请求。原用户表的登记时间单独展示，不作为首次使用时间；
`/stats` 单独展示统计启用前已登记的账号数量，不与新统计的用户数相加，避免重复计算。

## 统计口径

- 接触：发送 `/start`、`/help`、`/lang`、`/cfg`，操作语言/设置按钮，发起内联查询，或提交解析。
  不记录无关群消息，也不把管理员查询本身计为使用。机器人账号和无法确定发送者的匿名消息不计入。
- 活跃：统计时区内今日，或含今天的最近 7 个自然日内有接触记录的去重账号。
- 普通解析：每个链接算一个请求，含私聊和能识别发送者的群聊。多链接消息分别计数；
  缓存命中也计数；同一个请求在流水线内部重试不重复计数。被限流、解析/上传失败记为失败。
- 成功：请求流程完成并发送预期结果，包含视频、图片、文件、图文和原链接结果。
  Raw/ZIP 上传失败明确返回失败；多文件任务只完成部分上传时不算整个请求成功。
- 内联：浏览建议只记接触；选中结果后才记请求。直接发送/缓存结果以 Telegram 的
  `ChosenInlineResult` 为确认；需要后台下载的结果以实际替换媒体成功为确认。
  这依赖 BotFather 的 `/setinlinefeedback` 设置为 `100%`。关闭或采样反馈会漏记内联交付，
  Telegram 内联缓存也可能使部分查询不抵达机器人；不能据此完整还原未收到的事件。
- 成功率：成功 ÷（成功 + 失败）；处理中和中断不参与分母。重启后未完成的任务记为中断。
- 首次接触、最近使用指统计启用后观察到的操作时间，不等于原用户表创建/更新时间。

## 存储与上游同步

数据保存在 `DATA_PATH/db/usage_stats.db`，默认容器路径为 `/app/data/db/usage_stats.db`，
沿用现有 `data` 卷，因此重新构建容器不会丢失统计。独立 SQLite 文件不参与上游 Alembic 迁移。
使用单个机器人进程写入此文件。

累计用户和累计计数持续保留；请求明细保留 30 天，每小时最多清理一次，查询和记录时触发。
只记录数字用户 ID、聊天 ID、时间、模式、站点域名和结果，不存完整资源链接、Cookie 或媒体。
统计数据库不可写时记录警告，继续执行原解析流程；该期间的统计可能缺失。

新增逻辑集中在：

- `extensions/usage_store.py`：独立存储、累计计数、明细清理。
- `extensions/usage.py`：统计装饰器、管理员与时区配置。
- `extensions/usage_menu.py`：管理员专属私聊菜单，不修改公共命令列表。
- `plugins/usage_stats.py`：联系人观察、管理员命令和用户列表按钮，通过插件机制自动加载。

上游代码仅接入四个文件：`plugins/parse/handlers.py` 的请求装饰器及 Raw/ZIP 结果透传，
`plugins/parse/sender.py` 的 Raw/ZIP 布尔结果，`plugins/parse/inline.py` 的内联结果装饰器和布尔结果，
以及 `bot.py` 在公共菜单初始化后调用管理员菜单设置。
同步上游后重点检查这四个接入点是否仍然保留，运行 `python -m pytest` 检查统计、菜单及用户列表测试。

部署：

```bash
docker compose up -d --build
```

旧的完整使用历史无法从现有用户表补回，本功能不推测或回填历史活跃和成功次数。
